Observed 2026-11-26 in the end-of-run review of Milestone 13 (head a8ece71, fixed in e7aa095). When `BucketStore::new` moved from a bare directory to `&ManagerRoots`, its root became the manager profile's bucket registrations. `bucket update` and `update --refresh` call `update_main`, which writes the zip, the staging directory and `main` under `self.root`. At the base (ff8074a) only `apps/modn-cli/src/bucket_update.rs` built the store from the shared data directory (`BucketStore::new(&data_directory()?)`); `update`, `update_refresh`, `module_releases`, `buckets` and `catalog_install` used `state_path.parent()` (the profile). With `--state-dir`, the refactored code wrote the official copy to `<profile>/buckets/main` while readers use `roots.official_main()` and failed with "cannot load local main bucket". The fix gives the update the shared data root; the regression test is `state_dir_keeps_the_official_main_copy_in_the_shared_data_directory` (`apps/modn-cli/tests/bucket_update_cli.rs:376@e7aa095`). A stale profile-local `main` left by a build with the bug is not migrated: the next update writes the shared copy and the stale one stays. Lesson: when a constructor changes from a path to a roots value, compare every call site with the directory it used at the base; the test suite did not cover `bucket update --state-dir`.
