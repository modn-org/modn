Finding: a stack that prompts first and re-plans after the prompt can commit members that the user never confirmed. The end-of-run review of Milestone 17 found this in `apps/modn-cli/src/catalog_install/commit.rs` at 0c2f79a6af41, and the fix landed in 02fb2a708092.

Failure trace: `install_stack` prompted for the members of `plan.members()`. Then `flow::acquire_and_replan` re-read the manager store and rebuilt the whole plan. The consent digest came from the new plan, so it always matched itself. A dependency that another process uninstalled during the prompt would add a member that the user did not confirm. `stack_approvals` also paired approvals with members by position, so a changed member list moved executable approvals to the wrong releases. The old `stack_install.rs` did not re-plan after the prompt.

Fix: `ConfirmedStack::of(plan)` records the member references, versions, install order, native-injector policy and executable coverage before the prompt. `ConfirmedStack::verify(plan)` runs after the re-plan and refuses with `PLAN_STALE` when anything differs. A Git release digest that acquisition learns after the prompt is not compared. `stack_approvals` now finds each check by release reference. Tests: `consent_tests.rs` (the `ConfirmedStack` cases) and the two `stack_approvals_*` tests in `commit.rs`.

A second gap in the same review: no test reached the under-lock stale check in `commit_plan`, because the existing stale test changed the game module before the pre-lock check. A `#[cfg(test)]` hook (`set_before_transaction_hook`) now changes the module between the pre-lock check and the transaction call, in `commit_tests.rs`, for a single release and for a stack.

Lesson: when a flow prompts and then acquires or re-plans, record what the prompt covered and compare it after the re-plan. Do not derive the consent digest from the plan that the re-plan produced.

Check the code with `rg -n "pub struct ConfirmedStack" crates/modn-core/src/catalog_pipeline/consent.rs`.
