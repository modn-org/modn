Observed 2026-11-26 while testing Milestone 14. After a plain catalog signer change and a new `modn bucket trust-modules`, an unchanged retained release keeps its old recorded signer. The release is then not trusted, and `modn module update <game>` refuses with a message that offers `modn bucket trust-modules <bucket>` or `modn module remove <game>`. Re-trusting alone does not restore updates. The recovery that works is `modn module remove <game>`, then `modn bucket trust-modules <bucket>`, which imports the release signed by the trusted signer; `apps/modn-cli/tests/module_update_signer_cli.rs` pins both the refusal and this recovery.

Known limit: the refusal text does not say that `modn module remove` must come first, and an unregistered source bucket gets the same "trust it again" remedy although `trust-modules` fails for an unregistered bucket (`apps/modn-cli/src/module_releases.rs:80@49bb249`, advisory finding of the Milestone 14 review).
