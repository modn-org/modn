Store::update_catalog_release withdraws the old release under a pending uninstall journal, installs the new release, and retires the old package in the new install's SQLite commit. Recovery rolls back pending installs before pending uninstalls.

The old package's ownership stays recorded until the commit, so a failure or crash restores it under the same package ID and dependents keep valid links. The install path accepts exactly the update's uninstall journal as pending and excludes the old package from ownership, directory and conflict checks. The commit order matters because SQLite foreign keys are enforced: free the old file and directory rows first, insert the new package, then re-point package_dependencies and delete the old package row. Recovery must roll back the install journal first: otherwise restoring an old file meets the new file at the same path and recovery refuses. update_tests::recovery_restores_the_old_release_after_an_interrupted_update fails with the reversed order. Cleanup of a committed uninstall now refuses only when the live folder still has the old exclusive folder's identity, because the new release legitimately recreates that folder. The update preview hides the old release's paths from the read-only Lua host, so the policy plans as for a fresh install. Issue #48.
