Decision: install, stack install and update share one plan routine and one commit routine in `crates/modn-core/src/catalog_pipeline/`. The CLI keeps only arguments, consent prompts and output. This was true at 02fb2a708092 on the branch `t3/catalog-install-pipeline` (Milestone 17, issues #223, #224, #225).

Reason: before Milestone 17, `install_mod`, `stack_install.rs` and `update.rs` each built their own plan and their own commit sequence. A shared core routine makes one place that decides what a plan holds and when a commit may start.

Shape of the decision:
- `plan_install` and `plan_update` return one `CatalogPlan` with a `#[non_exhaustive]` `PlanKind` (`Install`, `Update`). The plan never prompts, never uses the network, never runs a game module and never writes. It reports refusals as data.
- `commit_plan(CommitRequest)` takes `&CatalogPlan`, `&Consent`, `&dyn SourceTransport`, `&dyn ReleaseResolver`, `SourcePolicy`, `CacheUse`, `&OperationControl` and `&mut Store`. The CLI opens and validates the writable `Store`.
- `commit_plan` acquires missing archives only through `ArchiveCache::acquire_release` (Milestone 16), before the lock. There is no second acquisition path.
- The lock, the journal and the ownership writes stay in `crates/modn-core/src/transactions/`. A plan is never authorization.
- `Consent` is plain data that the CLI builds after prompting. Nothing derives it from a plan. `commit_plan` repeats the native-injector and executable-coverage checks itself.

Check the code with `rg -n "pub fn commit_plan" crates/modn-core/src/catalog_pipeline/commit.rs` and `rg -n "pub enum PlanKind" crates/modn-core/src/catalog_pipeline/plan.rs`.
