Modn stores one approval per catalog mod, bucket and game installation, keyed by (game_path, bucket, mod_id), in the mod_approvals table. It records whether native code is approved and the set of approved game-relative executable paths. An approval of one bucket never covers a same-named mod of another bucket. A committed install or update stores or widens the approval; a cancelled, refused, dry-run or rolled-back operation stores nothing; uninstall keeps it; a release that drops a capability does not shrink it. Explicit executable flags are not stored as an approval. As of the #173 change on dev (2026-11-28), commit_plan stages the needed approvals with Store::stage_approvals. Store::commit_install writes a single release's approval in the ownership transaction, and finish_stack writes stack approvals in the stack-finishing transaction. A failed approval write rolls back the ownership change. The earlier known gap (approval in a second SQLite transaction after the commit) is closed. Tests: crates/modn-core/src/catalog_pipeline/tests/approval_commit_tests.rs.
