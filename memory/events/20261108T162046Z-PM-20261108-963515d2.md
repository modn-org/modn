Finding, 2026-11-08, from issue #140. On Linux, `flock` belongs to the open file description. A child forked to start `git` inherits the lock descriptor and keeps the lock until `exec` closes it. A sync that starts in that window sees `.git-sync.lock` or `.main-update.lock` as held and failed with "already running" on Ubuntu CI. Fix: `buckets/lock.rs` opens the lock file, retries only contention errors every 25 ms for up to 2 seconds, then returns the same message. Other I/O errors still fail at once. Do not replace this with a blocking lock without a timeout: a stuck process would hang the command. Tests: `buckets::lock::tests`, `buckets::git::tests::sync_waits_for_a_short_held_lock`, `buckets::git::tests::sync_reports_already_running_while_the_lock_stays_held`, and the matching `buckets::update::tests` cases.
