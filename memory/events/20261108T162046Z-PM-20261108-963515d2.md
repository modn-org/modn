Finding, 2026-11-08, from issue #140. A Git catalog sync test failed once on Ubuntu CI with "Git catalog sync already running" and passed on rerun. The failure was not reproduced. Likely cause: on Linux, `flock` belongs to the open file description. A child forked by another thread to start `git` inherits the lock descriptor and keeps the lock until `exec` closes it. A sync that starts in that window sees `.git-sync.lock` or `.main-update.lock` as held. Fix: `buckets/lock.rs` opens the lock file, retries only contention errors every 25 ms for up to 2 seconds, then returns the same message. Other lock errors fail at once with "cannot lock <path>". If "already running" flakes return, this cause is wrong. Do not replace this with a blocking lock without a timeout: a stuck process would hang the command. Tests: `buckets::lock::tests`, `buckets::git::tests::sync_waits_for_a_short_held_lock`, `buckets::git::tests::sync_reports_already_running_while_the_lock_stays_held`, and the matching `buckets::update::tests` cases.
