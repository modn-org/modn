As of 79c70e1 (2026-11-13), Modn stores one approval per catalog mod and game installation, keyed by `(game_path, mod_id)`, in the `mod_approvals` table (manager schema version 5). It records whether native code is approved and the set of approved game-relative executable paths.

This narrows the per-command opt-in rule in PM-20261107-43a82f2b. `--allow-native-injector` and `--allow-executable` still exist, and an install or update whose release capabilities the stored approval does not cover is still refused with `NATIVE_INJECTOR_NOT_ALLOWED` or `APPROVAL_REQUIRED`. The difference is that a committed install or update stores or widens the approval, so a later release that the approval covers needs no flag. A release that adds a capability asks again. A cancelled, refused, dry-run or rolled-back operation stores nothing; uninstall keeps the approval; a release that drops a capability does not shrink it.

Only the CLI backend writes approvals; MCP and desktop inherit the stored decision. There is no revoke command. The key does not include the bucket, so two buckets that publish the same mod ID share one approval; a bucket-qualified key is a separate policy and schema decision.

Known gap: the approval is written in a second SQLite transaction after the install or update commits. If that write fails, the mod stays installed and the approval is not stored. A repeat of the same command does not repair it, because the release is already installed or up to date. The gap fails closed: a later release that needs a capability asks again or is refused without the flag, and no capability runs without an approval or flag.

This corrects PM-20261112-0056b0ee, which said that a rerun with the flag repairs the gap.
