The official main bucket moved from buckets/main to the public modn-org/main repository, with its 17-commit history (git subtree split). `modn bucket update` fetches main-bucket.zip and its .sha256 from the latest modn-org/main release (first: v2026.11.04). Modn releases no longer publish main-bucket.zip. modn pins a bucket commit as the buckets/main submodule for its tests, smoke tests and verify-modn. The bucket CI builds the modn revision in .github/modn-ref. It packs only bucket.json, PROVENANCE.md and games/, runs bucket update and search against the ZIP, and (from modn-org/main#1) dry-runs install for every package, so dependencies and version requirements must resolve. A v* tag publishes the validated ZIP. The bucket repository forces LF. ZIP bytes repeat only within one Python and zlib build: a Windows zlib-ng pack and the Linux CI pack hold the same files but compress differently, so only CI publishes releases.

Constraints found on 2026-11-04: modn-org is on the free plan. modn-org/modn was private until the user made it public on 2026-11-04, so modn-org/main CI could not check out modn before then. The only modn release, v0.1.0, has no `modn bucket update`, so the bucket CI pins a modn commit (c5ce1ad) instead of a release. Change .github/modn-ref to a release tag once a release includes bucket update. The host API rule already holds: validate_manifest rejects an api_version other than HOST_API_VERSION before the swap. bucket_update_cli pins that rule. modn's official_catalog test covers only modn's pinned bucket copy, so the bucket repository needs its own resolution check.

Supersession reason: Review of PR #72 found two errors. ZIP bytes depend on the zlib build, not only on line endings. The bucket CI also did not resolve dependencies; modn-org/main#1 adds that check.
