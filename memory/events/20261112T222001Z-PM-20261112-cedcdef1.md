As of dae625e (2026-11-12), `modn undo [<operation-id>] --yes` reverses one committed operation through the normal transactional install, update and uninstall paths. It is not a special writer. An undo of an install uninstalls the packages it installed; an undo of an update restores the release each package had before; an undo of an uninstall installs the removed release again, and the archive SHA-256 must equal the recorded one.

An undo writes a normal history record for its effect and sets the nullable `undoes` field to the target operation ID. Because that record is newer and touches the same files, the conflict rule needs no special case: undo refuses with `UNDO_CONFLICT`, before any change, when a later operation on the same installation touched a file or package the target touched. A second undo of the same target is refused the same way.

Restoring a release needs its archive. Undo looks in the archive cache first for every non-manual source. An `https` or `github-release` source that is not cached is downloaded again. A `git` or `nexus` source is restored only from the cache; on a cache miss undo refuses with `UNDO_FAILED` before any change, because Modn cannot fetch that source again (a Nexus download needs a new nxm link). A `manual` source cannot be fetched again at all, so undo refuses with `UNDO_SOURCE_MANUAL` before any change. Other refusals are `UNDO_NOT_FOUND`. A multi-package record is undone all or nothing in one stack or one multi-package removal. Undo reports progress and accepts a stdin `cancel` before its commit point.

This corrects PM-20261112-cd156dcc, which recorded Git and Nexus undo as refused even when the archive is cached. The end-of-run review found that gap, and the fix is in dae625e.
