Milestone 15 (issues #167, #168, #169, #170) gave game-module release admission and activation one owner that survives a process death.

Decision 1: one admission routine. `admit` in registry/admission.rs computes the BLAKE3 digest, refuses a same version with a different digest, applies the pin, stages with `check_module` and compares versions. Both `import_verified` and catalog `stage_one` call it.

Decision 2: activation runs under an intent file. `write_intent` writes `activation.json` atomically before the first version-directory move. It lists each release with its version, digest and previous `current` value. `ModuleRegistry::open` repairs a leftover intent: it verifies each version directory against the intent digest, then writes the `current` pointers (roll forward). If a release does not verify, it rolls the whole set back. Repair changes only directories and pointers. It never writes module bytes.

Decision 3: sync does not activate an inactive retained release. On disk, such a release cannot be told from a deliberate rollback, and the rollback test would break. The intent file is the only discriminator. The planned sync-level rule was dropped for that reason.

Decision 4: a Git catalog sync verifies the catalog, stages its modules, commits them, and only then publishes the bucket registration. The modules were checked against the signed catalog snapshot, so committing them first adds no trust. A failed module commit leaves both sides on the old state. A failed publish converges on the next sync.

Evidence: the process-death test is crates/modn-core/tests/module_activation_recovery.rs. It was recorded failing on the old code in commit 1a99ca1 (left Some("1.0.0"), right Some("2.0.0")). A lib test stops `apply` after the moves without `restore`.
