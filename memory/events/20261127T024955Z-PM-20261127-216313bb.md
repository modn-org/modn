Decision: a stale plan is detected by a re-plan under the transaction lock and a comparison of a canonical `PlanDigest`. A mismatch is a typed `StalePlan` refusal with the stable code `PLAN_STALE` (`ErrorCode::PlanStale`) and no write. There is no fingerprint pre-check. This was true at 02fb2a708092 (Milestone 17, issue #224).

Reason: a pre-check of the store or of the game module would race with the lock. Only the re-plan under the lock sees the facts that the commit writes against. The transaction layer gets entry points that take a re-planning closure: `install_catalog_release_planned` and `update_catalog_release_planned`. The journal and recovery code did not change.

What the digest covers: install order, release digests, dependency and conflict facts, native-injector policy, approved executables, the per-member policy preview, the game id and the canonical installation path. It excludes archive paths, served status and pending downloads, because acquisition legitimately changes those.

Consequences:
- The digest carries the tag `v1`. A change to its encoding must bump the tag.
- A game module whose output changes between the prompt and the commit now ends as `PLAN_STALE`, where an update could earlier end as `PLAN_BLOCKED`. An update commit compares the refreshed digest before the reviewable check.
- `code_of` needs typed arms for `StalePlan` and `ApprovalRefusal` (`crates/modn-core/src/error.rs`), because anyhow downcasts only the outer context type.

Check the code with `rg -n "pub struct StalePlan" crates/modn-core/src/catalog_pipeline/consent.rs` and `rg -n "PlanStale" crates/modn-core/src/error.rs`.
